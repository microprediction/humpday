# benchmarks

Four artifacts live here and they answer three different questions. Confusing them is easy and was
the reason this file exists: until recently three separate rating tables, built by different scripts
at different times over different objectives, fed different parts of the library, so `minimize` and
`suggest` could disagree about the same problem.

## Which optimizer should I use? — `humpday/data/ratings.json`

The one rating table, and the only one any recommendation reads. It does not live here; it ships
inside the package, because a recommendation must not need a benchmark run or a network. This
directory holds the recorder and the raw shards it writes.

| | |
|---|---|
| Recorder | `record_ratings.py` |
| Raw shards | `ratings_cells/<dim>_<budget>_<suite>.json`, one file per cell |
| Shipped table | `humpday/data/ratings.json` (merged from the shards) |
| Read through | `humpday.ratings` — never by opening the file |

Indexed by **dimension**, **evaluation budget** and **objective suite**, because all three change
the answer. See the module docstring of `humpday/ratings.py` for why dimension is never
interpolated, why budget is interpolated downward only, and why the two suites are never averaged.

```bash
python benchmarks/record_ratings.py                   # everything missing, all cores
python benchmarks/record_ratings.py --dims 50,100     # just the expensive end
python benchmarks/record_ratings.py --problems 40     # deepen what is already there
python benchmarks/record_ratings.py --merge           # rebuild the shipped table only
```

It resumes rather than restarts, skips a cell already deep enough, and writes each cell as soon as
it finishes, so it can be interrupted and re-run in pieces. Re-run it after any change to optimizer
logic; a cell recorded against different code is not evidence about the current code.

## How does the recommender behave across a dense grid? — `recommendation_grid.json`

Borda mean-ranks over nine analytic surfaces at 11 dimensions and 3 budgets. Denser than the
tournament and narrower: analytic surfaces are smooth, smoothness rewards local search, and
`papers/dfo_recommender/benchmark_validity.tex` is about what that does to a ranking.

It stays for two reasons that are not "the recommender needs it". It is the dataset
`papers/dfo_recommender/analysis.py` analyses, and it is the asset the JavaScript port ships
(`docs/js/modules/recommendation-grid.js`, generated by `build_js_grid_asset.py`). Inside
`humpday.eligibility.recommend` it sits *below* the recorded tournament and is consulted only where
that has nothing to say. Rebuild with `build_recommendation_grid.py`, then regenerate the JS asset.

## Are the JavaScript ports faithful? — `port_characterisation.json`, `reference_alignment.json`

Nothing to do with recommending an optimizer. These are port-fidelity baselines: measured
Python-versus-JavaScript behaviour (`tests/test_port_behavior.py`, `notes/PORT_EQUIVALENCE.md`) and
alignment against the pre-online reference implementations (`tests/reference_impls_pre_online.py`).
A regression here means a port drifted, not that an algorithm got worse at optimising.

## What was deleted, and why it is not coming back

`elo_ratings.json` and `record_elo.py` raced sphere and Rosenbrock variants in **two dimensions** at
a flat 100 trials. Two dimensions is not a setting anyone needs advice about, and a flat budget
below what a trust-region method needs to build its interpolation set scores it for returning
without a model — which is how the PRIMA trio came to be bottom-three on a leaderboard they now
sweep. `record_elo_by_dimension.py` and `elo_by_dimension.json` were the right idea without budget
in the index; `record_ratings.py` is their successor.
